# Перенос ROM через GitHub Actions

Workflow **Port ROM** запускает существующий `port.sh` вручную и сохраняет
готовые ZIP и `SHA256SUMS` на Pixeldrain. Загрузки в артефакты GitHub нет,
включая журналы; ссылки и SHA-256 выводятся в Summary запуска.
Он не добавляет поддержку новых устройств: для realme GT 2 Pro по-прежнему
нужна отдельная адаптация под устройство и выбранную пару прошивок.

1. Отправьте изменения в свой репозиторий GitHub. Workflow с
   `workflow_dispatch` должен присутствовать в default branch, чтобы появилась
   кнопка запуска. В форке при необходимости включите Actions.
2. Создайте ключ на https://pixeldrain.com/user/api_keys и добавьте его в
   **Settings → Secrets and variables → Actions → New repository secret**
   под именем `PIXELDRAIN_API_KEY`. Ключ не вводится в параметры workflow
   и не хранится в репозитории. Ваш тариф Pixeldrain должен допускать размер
   итоговой прошивки и иметь достаточно свободного места.
3. Откройте **Actions → Port ROM → Run workflow** и выберите ветку,
   соответствующую поколению Android, например `COS16/OOS16`.
4. Укажите прямые HTTPS-ссылки на полные ZIP базовой и донорской ROM.
   Страницы скачивания, инкрементальные OTA и ссылки, требующие cookies,
   не подходят. Используйте пакеты, которые вы вправе скачивать и обрабатывать.
5. При необходимости укажите второй донорский ZIP и список разделов из него
   через запятую, например `product,my_product`. Эти два поля заполняются вместе.
6. После успешного выполнения откройте **Summary** запуска: там будут ссылки
   Pixeldrain на ZIP и файл контрольных сумм. При ошибке проверьте консоль
   соответствующего шага и **Show failure logs**. Отдельных артефактов нет.

Ключ проверяется на наличие до скачивания ROM. Загрузка выполняется через
официальный `PUT /api/file/{name}` с Basic Auth и включённой проверкой TLS.
Скрипт проверяет ответ API, идентификатор и размер принятого файла; сетевые
ошибки и временные ошибки сервера повторяются до трёх попыток. Отказ API,
нехватка квоты и превышение допустимого размера файла завершают шаг ошибкой.
Реальную загрузку с вашим аккаунтом нужно проверить после добавления секрета.
Поддерживаются ответы PUT без поля `success`, включая ответ только с `id`.
Если размер отсутствует, он проверяется через `GET /api/file/{id}/info`.
Ссылка выводится сразу после получения ID; ошибка проверки метаданных
не вызывает повторную загрузку уже принятого файла.

Настройки упаковки берутся из `bin/port_config` выбранной ветки. Зависимости
устанавливаются отдельно от `setup.sh`, без полного обновления ОС.
ROM скачиваются через aria2, включая второго донора. Базовая и донорская
ROM загружаются одновременно, по четыре соединения на файл. Загрузчик
передаёт заголовки OPlus для ссылок downloadCheck, следует редиректам,
поддерживает докачку и повторные попытки. Прогресс виден в журнале Actions.
Проверка сертификатов включена, после загрузки проверяется целостность ZIP.
Незавершённая загрузка с контрольным файлом `.aria2` не передаётся в сборку.
Скорость ниже 64 КиБ/с приводит к повторной попытке, сетевые паузы ограничены
30 секундами. Жёсткий лимит шага скачивания — 90 минут, портирования —
240 минут. Скачивание через специальный Python-скрипт больше не требуется.
Выходной код `port.sh` сохраняется, готовые ZIP проверяются через `unzip -t`,
а отсутствие выходного архива считается ошибкой. Это не проверяет загрузку
прошивки или работу оборудования на телефоне.

По умолчанию используется `ubuntu-24.04`, лимит job — шесть часов.
Перед скачиванием требуется минимум 30 ГиБ свободного места; это лишь нижняя
граница, не гарантия достаточного объёма для конкретной пары ROM. Для больших
образов выберите `self-hosted`: нужен отдельный одноразовый Linux x64 runner
на Ubuntu 24.04 с `apt-get`, Python 3 и беспарольным `sudo`, достаточным диском
и метками `self-hosted`, `Linux`, `X64`. Не используйте runner с личными файлами
или постоянными секретами: сборка исполняет инструменты выбранной ветки.

Ссылки вводятся как обычные параметры Actions и не являются секретными.
Не вставляйте токены или приватные подписанные ссылки. Учитывайте доступность журналов и Summary участникам репозитория,
публичные ссылки Pixeldrain, ограничения тарифа и минуты Actions.
Workflow не публикует релиз и не прошивает устройство.

В Actions включён `PORT_LOW_DISK=true`: после распаковки удаляются загруженные
копии ROM из `build/ci-inputs`, дубли образов в кэше и затем, перед созданием
OTA, рабочие деревья `build/baserom`, `build/portrom` и `tmp`. Подготовленные
target-files, журналы и финальные архивы сохраняются. Локально этот режим
выключен; не включайте его, если нужны промежуточные файлы для отладки.
Файлы для загрузки на Pixeldrain помещаются в `build/ci-uploads` жёсткими
ссылками: дополнительная копия ZIP на диске не создаётся.
Снижение расхода диска не гарантирует, что любая ROM поместится на стандартный
runner. Предыдущий сбой `No space left on device` возник при записи payload.

Очистка донора выполняется после распаковки и до применения патчей по списку
`bin/donor-debloat.txt`. Удаляются только указанные пути внутри `my_product`
и `my_stock`; шаблон `SystemUiFingerprintRes*` действует только в каталоге
`my_product/overlay`. Для intuition_wallpaper учтены варианты `commin` и
`common`, включая дополнительный уровень `my_product` из исходного списка.
Донорские камера и product_overlay удаляются до установки камеры и необходимых
ресурсов из базовой прошивки. Исходные архивы вне каталога CI не изменяются.
Удаления видны в `ci-port.log`. Список можно изменить перед запуском; удаление
пакета из списка не восстанавливает то, что уже удаляет прежняя логика порта.

Локальная загрузка тем же способом, что и в Actions:

```shell
source functions.sh
port_download_rom 'https://example.com/base.zip' "$PWD/build/ci-inputs/base.zip"
```

Python-загрузчик остаётся отдельным необязательным инструментом. Для него нужны
`requests` и `tqdm`. Пример использования:

```shell
python3 bin/oplus_ota_downloader.py --output build/ci-inputs --name base.zip 'https://example.com/base.zip'
python3 bin/oplus_ota_downloader.py --metadata 'https://example.com/base.zip'
python3 -m unittest discover -s tests -v
python3 tests/smoke_wallpapers_patch.py
```

Для `--metadata` сервер должен поддерживать точные byte-range запросы.
Метаданные читаются отдельными диапазонами без выделения памяти под полный ROM.
Опция `--md5` позволяет сверить скачанный файл с известной MD5; без неё
проверка длины и ZIP не подтверждает подлинность прошивки. При передаче URL
непосредственно в `port.sh` используется aria2.

При патче `Wallpapers.apk` apktool работает с `--no-res`: меняется dex, а исходные
бинарные ресурсы и манифест сохраняются. Это устраняет ошибку сборки OEM
styles.xml (`expected reference but got ...`) и исключает лишнюю обработку
ресурсов. Smoke-тест проверяет сохранность ресурсов и изменение dex реальными
apktool/smali. При упаковке fastboot-прошивки zstd использует все доступные
ядра; ZIP сохраняет уже сжатые файлы без повторного сжатия.

В репозитории закреплён официальный apktool **3.0.3** вместо старого
2.9.0-SNAPSHOT. Источник и SHA-256 записаны в `bin/apktool/APKTOOL_VERSION.md`;
Actions проверяет контрольную сумму перед запуском тестов. Для dex-only патчей
Wallpapers сборка использует `--copy-original`, сохраняя исходный бинарный
манифест. Тест `smoke_apktool_resources.py` проверяет установку framework,
декодирование и пересборку ресурсов с изменением Wi-Fi bool. Проверка на
полном framework-res.apk конкретной донорской ROM требует нового запуска.

Для портов ColorOS 17 (Android 17) в `oplus-services.jar` очищается тело
`OplusEngineerFwService.onBootPhase(I)V` до `.locals 0` и `return-void`.
Также удаляется `vendor/app/soterservice`. Для Android 16 и ниже эти действия
не выполняются. Патч использует отдельный кэш JAR; отсутствие нужного класса
или метода завершает сборку явной ошибкой. Автоматическая проверка прогоняет
тестовый JAR через настоящие APKEditor/smali, но исправление зависания на
втором экране загрузки необходимо проверить на целевом устройстве.

Патчинг `OTA.apk` отключён: приложение не заменяется файлами OTA_CN/OTA_IN,
не берётся из кэша патчей и не пересобирается. Это относится только к приложению
обновления; генерация итогового OTA ZIP через `ota_from_target_files` сохранена.
